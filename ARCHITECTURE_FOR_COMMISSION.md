# Архитектура ИС поддержки принятия решений (для комиссии)

## 1. Цель системы
Система предназначена для руководителя малого предприятия и решает задачи управленческого финансового учета:
- учет выручки и затрат;
- анализ прибыли и рентабельности;
- контроль отклонений от бюджета;
- прогнозирование на основе исторических данных;
- формирование управленческих рекомендаций.

Важно: система не является бухгалтерской системой регламентированного учета. Это инструмент управленческой аналитики и поддержки решений.

## 2. Архитектурная схема
```text
Database (PostgreSQL)
  -> finance_engine (централизованные расчеты)
    -> ai_engine (интерпретация показателей, прогнозный текст)
      -> recommendation_engine (правила + AI-слой)
        -> Frontend (дашборд, операции, аналитика, система)
```

Принцип: контроллеры не считают бизнес-метрики. Они только принимают/валидируют запрос и вызывают соответствующий engine.

## 3. Модули
### 3.1 Database
Хранит пользователей, операции, справочники, бюджеты, аудит и служебные настройки.

### 3.2 finance_engine
Единая точка расчетов:
- `get_summary`, `get_monthly`, `get_kpi`;
- `get_categories_monthly`, `get_baseline_monthly`;
- `run_scenario` (управленческий сценарий);
- `data_quality`/`fix_uncategorized_operations`;
- `ai_forecast` (прогнозные ряды на базе исторических данных).

### 3.3 ai_engine
Получает уже посчитанные показатели и формирует текст аналитики через внешний AI API.
Самостоятельных финансовых расчетов не делает.

### 3.4 recommendation_engine
Собирает rule-based рекомендации + при наличии ключа/доступа дополняет их AI-результатом.
При ошибке внешнего API возвращает fallback на rule-based слой.

### 3.5 Frontend
Единый интерфейс:
- операции (выручка/затраты);
- структура (статьи, подразделения, проекты);
- аналитика и решения;
- системный центр (импорт/экспорт, история действий).

## 4. Модель данных (основные сущности)
- `users`
- `categories` (P&L: income/expense)
- `departments`
- `projects`
- `income`
- `expense`
- `operation_dimensions` (связка операции с подразделением и проектом)
- `monthly_budgets`
- `category_limits`
- `audit_logs`
- `user_settings`

Операция хранится в `income`/`expense`, а обязательное подразделение и опциональный проект задаются через `operation_dimensions`.

## 5. Ключевые связи и ограничения
- `income.user_id`, `expense.user_id` -> `users.id`
- `income.category_id`, `expense.category_id` -> `categories.id` (NOT NULL)
- `operation_dimensions.department_id` -> `departments.id` (NOT NULL)
- `operation_dimensions.project_id` -> `projects.id` (NULL, опционально)
- уникальность размерностей операции: `uix_operation_dimension(transaction_type, transaction_id)`
- уникальность категорий/подразделений/проектов в рамках пользователя.

Целостность достигается комбинацией FK + валидации на backend (дата, сумма, статья, подразделение).

## 6. Роли и доступы
- `owner`: полный доступ
- `manager`: чтение + создание/изменение операций и структуры, без удаления операций
- `accountant`: полный доступ к операциям и системным функциям
- `department_head`: чтение аналитики и операций без CRUD

Модель "одна компания = много пользователей" реализована через `company_owner_id` в `user_settings`.
Это дает единый контур данных для команды.

## 7. Единый механизм обновления
Любое CRUD-изменение операций (`income`/`expense`) сразу влияет на API-метрики:
1. обновляются агрегаты `finance_engine`;
2. пересчитываются KPI и baseline;
3. обновляется прогноз (`ai_forecast`);
4. обновляются рекомендации (`recommendation_engine` + `ai_engine`).

Итог: реализован сквозной цикл
`Операции -> Аналитика -> KPI -> Прогноз -> Рекомендации`.
